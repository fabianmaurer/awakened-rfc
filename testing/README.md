# AI-only observer recordings

All external test launchers, analysis tools, configuration and recordings live
in this `testing/` directory. Launchers can be double-clicked from here;
Python command examples below assume the repository root as the working directory.
Existing recordings are preserved under `testing/runs/`. Game-side observer
hooks remain in the mod source because Civ4 loads them from there.

## Working with the assistant

1. Describe the test you want: purpose, mode, game count, duration and any
   specific settings or seeds.
2. The assistant creates a standalone script with that configuration and
   gives you its path. It does not launch the game or poll progress.
3. Run the script yourself. The launcher manages its own progress monitoring
   and writes the recordings to disk without an active assistant session.
4. Ask the assistant to analyze the resulting run/batch folder when ready.

Requesting a test script does not authorize the assistant to execute it.

The observer is opt-in development tooling. Normal launches do not register
observer event handlers, collect state, seed RNGs or write recordings. Its
module performs no XML lookups during import. Python 3.9+ is needed only for
the external launcher and analyzer, not to play the mod.

## Run a batch

From the repository root in PowerShell:

```powershell
.\testing\run-test --mode diagnostics --start 0 --runs 5 --turns 150
.\testing\run-test --mode performance --start 2 --runs 1 --turns 150 --seed 1
.\testing\run-test --help
```

Modes are `balance`, `diagnostics`, and `performance`. Starts are zero-based:

| `--start` | Scenario | Observer |
| --- | --- | --- |
| 0 | 3000 BC | America |
| 1 | 800 BC | America |
| 2 | 600 AD | China |

`--runs` sets the total number of games. `--turns` counts simulated turns
from the scenario start. Seeds begin at `--seed` (default 1) and increment for
each run. All existing launcher options remain available, including output and
checkpoint intervals. Without `--turns`, the local configuration applies,
falling back to 500. Add the `testing` directory to your shell PATH yourself if
you want to invoke bare `run-test` from any directory. The wrapper does not pause
on completion and preserves the launcher's exit code.

### Parallel mechanics and balance runs

```powershell
.\testing\run-test --mode diagnostics --start 0 --runs 5 --turns 150 --jobs 2
```

`--jobs` defaults to 1. With 2, at most two launcher-owned games run concurrently.
Parallel batches pass Civ4's `multiple` option to every child, including the first,
to allow additional instances past the executable's startup guard.
Setup is serialized: the next instance launches only after the current setup
reports that initialization and its initial snapshot/checkpoint have finished.
This keeps foreground keyboard confirmation exclusive to one setup window.
Keep the desktop unlocked. Background instances must continue simulating for
parallelism to improve throughput; actual multi-instance behavior needs local
validation. Start with two workers.

Parallel execution requires unattended balance or diagnostics mode. Performance
mode rejects `--jobs` above 1 because competing processes distort measurements.
Each game has its own token, PID, observer output and checkpoint directory.
Civ4's ordinary profile, cache and standard logs remain shared; ordinary logs
may be overwritten or interleaved. Do not change settings while the batch runs.
Observer autosaves remain suppressed. The launcher initially requires Civ4 to
be closed, and stops only its own child processes. A failed run cancels pending
runs and stops active sibling runs, preserving partial recordings. Ctrl+C also
cleans up the batch's children. Existing unrelated processes are never killed.
`batch.json` records finished/cancelled active games in seed order.

For three balance games of 500 turns, using seeds 1-3 and snapshots/checkpoint
saves every 25 turns:

```powershell
.\testing\run-test --mode balance --start 0 --runs 3 --turns 500 --seed 1 --record-interval 25 --checkpoint-interval 25
```

Run locally with Civ4 closed and the desktop unlocked. Recordings default to
`testing/runs/`; use `--output-dir` to choose another parent directory.
The former preset test `.bat` launchers have been replaced by this CLI.

Batch folder names include mode, control type, scenario, game count, turn limit,
seed range and timestamp; individual game folders include mode, control type,
turn limit and seed. Reports generated by the analyzer remain in those folders.

Close Civ4 and synchronize the workspace runtime files and compiled DLL into
the installed `Mods/Awakened RFC` folder. The launcher compares SHA-256
fingerprints of both copies and refuses to mix different builds.

```powershell
python testing/run_observer.py --mode balance --games 10 --turns 500 --seed 1
python testing/run_observer.py --mode diagnostics --turns 100 --checkpoint-interval 25
python testing/run_observer.py --mode balance --turns 250 --record-interval 25 --checkpoint-interval 25
```

All modes support the four installed scenarios. Loaded saves are rejected.
Runtime validation checks each scenario's expected starting turn, start year,
and WorldBuilder filename when available. If the filename is unavailable,
metadata marks this and validation relies on turn/year checks and the launcher's
fixed scenario path/fingerprint. Seeds increment across the batch. The seed is
applied to both RNGs at GameStart, before RFC setup; the executable has already
loaded the map and initial placement by that point. This is recorded explicitly
in metadata, rather than claiming to seed earlier executable initialization.

The launcher targets the Steam executable by default; override with `--exe`.
It uses Civ4's `/fxsload` scenario argument. AI-only runs now automatically
confirm scenario setup for each game in the batch. An authenticated WorldBuilder
hook restricts the human selector to the scenario observer, sets Prince/Normal, and signals the
launcher when the correct scenario has loaded. Other civilizations still spawn
and play normally. The launcher brings only its own game window forward and
sends Enter's physical scan code to advance setup, with at most four attempts.
Setup polling runs every 50 ms. Confirmation retries wait at least 350 ms after
the preceding key release, following a 250 ms initial readiness delay. Keyboard
focus settles for 200 ms, and Enter is held for 100 ms for DirectInput polling.
After bringing the game forward it waits for keyboard focus to settle before
pressing the key. `setup-input.log` records focus waits and each confirmation;
the launcher prefers an already focused game window, restores minimized game
windows, and retries foreground activation through the Windows input queue.
if Windows refuses focus, select the game window to allow startup to continue.
It stops sending input
as soon as GameStart begins, before RFC initialization. Native error dialogs
stop the run instead of being dismissed. No screen coordinates or extra
automation packages are required, and the user's CivilizationIV.ini is unchanged.

Keep the Windows desktop unlocked and available to Civ4 during startup; do not
type into the game while automatic setup runs. This is desktop automation, not
headless execution. Use `--manual-start` to disable setup confirmation for
troubleshooting; `--observe-only` always leaves setup manual. The launcher waits
up to five minutes for GameStart by default. The new automatic setup path still
needs validation in a user-operated short run before relying on a large batch.

The AI observer preserves the active civilization, its cities and units. It
suppresses Civ4's initial and periodic autosaves for the AI test session,
including the final turn after AI control stops. Explicit observer checkpoint
saves remain controlled by `--checkpoint-interval`. The suppression is transient,
is not saved, and does not change normal-game autosave settings or `--observe-only`.
It does not call RFC's existing `setAIAutoPlay`, which deletes that player's
possessions. While explicitly enabled, all civilizations use their AI paths
and the game can continue without a surviving human civilization.
AI simulations use an **interface-only black progress screen** with a centered
green progress bar on a white track. Map rendering, normal HUD/minimap/scoreboard
refreshes, and spectator reveal overrides are disabled. No zoom setup runs.
Movement display, combat presentation, enemy glow and mission-animation delays
are suppressed only while observer AI control is active. This includes balance,
diagnostics and performance simulations; ordinary games and `--observe-only`
retain their normal presentation. User graphics/player preferences are not
rewritten. Actual moves, combat resolution, AI visibility and recording continue.
The screen still requires a running Civ4 process; this is not a headless server.

Enemy-sighting warnings are suppressed and old on-screen event messages are
cleared each turn during AI observer control. Their real-time lifetimes would
otherwise let flashing icons accumulate across rapidly simulated turns. Normal
play and observation without AI control retain the ordinary notifications.
Periodic historian rankings (such as "the most powerful civilizations") and
technology, wonder, era, introduction and victory presentation screens are
also suppressed during AI observer control. Their underlying gameplay effects
remain active; no gameplay decisions are auto-dismissed by this screen guard.

`--observe-only` records a manually played game without enabling AI control.
This is independent of recording mode. It is still a finite launcher session:
the launcher closes its child game when the requested recording ends.

Use `--startup-timeout` and `--stall-timeout` to accommodate slow loading,
long late-game turns or manual play. On completion, failure or timeout the
launcher terminates **only the game process it created** and stops a failed
batch rather than silently counting missing games. Turns are flushed and
checkpoint saves are written before completion. It never terminates a game
that was already running.

## Activation and safety

Copy `testing/observer.example.ini` to `testing/observer.local.ini` for optional launcher
defaults. That file alone cannot activate instrumentation. The launcher
creates a private per-run configuration and passes its path and a random
token only to the child process. The mod requires a matching token **and
process ID**. The configuration is removed afterward; even if the launcher
crashes, it cannot activate a later ordinary launch.

Recordings default to the ignored `testing/runs/` directory. Use
`--output-dir` to choose another location. Neither that directory nor the
local configuration is part of the playable release package. The dormant
runtime module is included because the event manager imports it.

Recording does not consume game randomness or write synchronized game data.
Experiment setup deliberately reseeds the RNGs; AI control is another separate
explicit mutation. This initial launcher rejects multiplayer, including
Pitboss/hotseat/PBEM. The observer flag is process-local and not serialized in
saves, so reopening a checkpoint normally does not enable AI control.

For 3000 BC and 800 BC observer runs, America is selected as the observer civilization. It
does not spawn during the first 150 turns (its ordinary spawn is turn 346).
If the setup screen retains Egypt or China, the observer transfers the active and human
slots to America before RFC initialization, leaving Egypt controlled by AI.
For 3000 BC the observer restores Egypt's playable flag because
RFC uses it to identify the early scenario. Other civilizations retain their
ordinary participation and spawn rules. The 600 AD observer remains China.

## Modes and output

### Performance-only recordings

For one AI-controlled **600 AD** game lasting **150 simulated turns**, seed 1,
Prince/Normal, with automatic setup as China:

```powershell
.\testing\run-test --mode performance --start 2 --runs 1 --turns 150 --seed 1 --startup-timeout 600 --stall-timeout 1800 --output-dir testing/runs/performance-600ad-150turns
```
The scenario starts at engine turn 181 (its StartYear remains -3000); the limit
counts completed turns from that start. Egypt's non-playable flag is preserved
so RFC's late-start initialization still recognizes the scenario.

The launcher accepts `--mode performance --scenario 600ad --turns 150`.
Performance mode also supports the default `--scenario 3000bc`. It requires AI
control, disables checkpoint saves, and skips gameplay snapshots, event payloads,
civilization tracking and diagnostic invariant scans. Activation and progress
files and exceptions remain available.

Performance mode applies the selected seed to both game RNGs during DLL
`CvGame.init`, before scenario initialization, rather than reseeding at GameStart.
The token/PID-bound `seed-initialized.ini` confirms the initialization stage and
effective seeds; a missing/mismatched marker stops the recording. No second
GameStart reseed discards the random draws made while initializing the scenario.
This earlier seeding and the new 150-turn duration establish a new benchmark;
older 100-turn recordings used later seeding and are not an identical replay.
Fixed seeds improve comparability but do not prove identical game trajectories
across mechanic changes or provide constant machine load.

Unit-AI boolean danger queries now stop at the first qualifying threat. Callers
that need exact threat counts retain the full scan. `unitAI.generatePath`
measures pathfinding; danger scan time stays in its parent AI scopes. Completion
elapsed time now uses the same high-resolution timer as turn boundaries.
`unitAI.AI_*Move` timers additionally distinguish combat, worker, exploration,
settler, missionary, naval and air roles. These include nested pathfinding and
danger timings; compare inclusive parent totals rather than adding them.

Trade-route selection now computes the origin city's attraction once per pass
and reuses candidate food pressure, infrastructure efficiency and base profit
instead of recalculating them for food demand and route income. Attraction is
not cached across route updates, and route-update timing and candidate ordering
are preserved. The next recording must measure the actual gain.

City AI road-connection planning checks candidate distance before pathfinding,
skipping cities that cannot beat the nearest disconnected candidate already
found. Candidate ordering and tie handling are preserved.
`cityAI.updateRouteToCity` measures this planning routine separately.

### Expanded parallelism assessment

Run `testing/Run Expanded Performance Profile.cmd` for one serial 3000 BC game,
seed 1, 400 turns, with a 600-second setup timeout and 1800-second stall timeout.
This launcher is user-operated; preparing it does not start a game.

The expanded DLL records city AI production/build/worker planning, plot culture,
trade influence, espionage visibility, player maintenance, diplomacy and game
turn substeps. Native callback scopes attribute Python event time within DLL
parents. Trade updates separate clearing, scoring/selection and commitment;
scoring still includes intermediate route assignments and revelation, so it is
not a pure worker-ready calculation. Search queue visits and scored candidates
are recorded as `work_units`; settlement-value batches also count native tile
evaluations without timing each tile. No gameplay order or RNG calls are changed.

`performance-native.csv` adds inclusive call-duration histogram bins (<0.1 ms,
0.1-1 ms, 1-10 ms, 10-100 ms, >=100 ms). Reports show calls, mean/max call size,
work units, inclusive/exclusive elapsed shares and exclusive milliseconds per
turn. Histograms identify where dispatch would need batching; they do not prove
that calls share unchanged inputs or may safely run concurrently.

`performance-runtime.csv` samples process and main-thread CPU time with Windows
accounting APIs once per native timing flush, plus cities, units and alive
players. Explicit start/end turns distinguish these intervals from Python
EndGameTurn intervals. CPU busy percentage distinguishes computation from time
off CPU, but off-CPU time does not uniquely identify rendering or waiting.
Function scopes still measure wall time, not individual function CPU time.

The analyzer reports the full pre-exception window and its last 100 recorded
turns, excluding the first affected turn onward. It includes p95 turn intervals
and optimistic 2/4/8-worker ceilings for candidate subsystems. These ceilings
assume full parallelizability and zero overhead; actual safe batching,
snapshot/commit overhead, worker scaling and multiplayer determinism require a
prototype and separate validation. Legacy recordings remain readable, with
missing CPU/histogram data identified as unavailable.

The very frequent `unitAI.plotDanger` timer is removed; its cost stays inside
parent unit-AI/path timers. Detailed per-node/path-destination logging remains
disabled. Additional profiling changes benchmark overhead, so compare future
implementations using this same instrumentation configuration.

### Plot-culture follow-up

The same `Run Expanded Performance Profile.cmd` includes targeted culture
diagnostics. The experimental lazy irrigation allocation and duplicate
working-city-refresh removal were reverted after the comparison showed no
measurable benefit. Original allocation and refresh behavior is restored;
diagnostic timers remain active during performance recordings.

Reports distinguish normal city-turn culture from explicit immediate ownership
updates. Timers under `culture.*` include only work nested inside
`CvCity::doPlotCulture`; equivalent `plot.*`/`plotGroup.*` timers capture other
callers. Real owner changes separate old/new sight, working-city assignment,
irrigation, yields, direct plot-group updates, unit validation and symbols.
Plot-group recalculation separates connectivity flood fills from rebuilding;
the counters show how often a check finds the existing group still connected,
and average group sizes. Checks triggered indirectly by visibility appear under
the corresponding sight scope as well as the nested group scope.

Culture call-duration bins now record elapsed seconds as well as call counts,
so the report can quantify how much time the rare slow calls consume. The
slowest-culture-turn table combines duplicate native flush rows and shows
ownership, network-check, rebuild and irrigation costs alongside culture totals.
Inclusive columns overlap. Historical recordings retain counters for avoided
irrigation allocations and duplicate working-city refreshes. New recordings
count the restored irrigation allocations without reporting avoided work.

This adds profiling overhead and does not establish a measured speedup. Network
updates still run immediately. Following the targeted comparison, plot-group
rebuilding now retains the reached component when its starting tile belongs to
the trade network and it contains more than half the original group. Only the
unreachable members are removed and reassigned, in their original list order,
through the existing resource-accounting methods. A membership/count mismatch,
invalid starting tile or small component retains the original full rebuild.

Connected groups still use one allocation-free connectivity check. A split
eligible for retention performs a second search to collect membership, followed
by incremental removal/reassignment. Timers distinguish `collectComponent`,
`incremental` and full fallback `rebuild`; counters record retained and detached
memberships. Compare the inclusive `plotGroup.recalculate` totals across all
callers, since the full-rebuild child alone no longer represents every split.
This changes internal group IDs/lifetimes and requires all multiplayer peers to
use the same DLL. Gameplay resource and connectivity behavior needs validation
in the user-operated run; no speedup or multiplayer validation is claimed.

Run the same 400-turn seed-1 launcher for the next comparison; no game is started
by building or analysing recordings.

### Historical path query detail

Detailed path-query collection is disabled: simulations no longer write
`performance-paths.csv`, count per-node callbacks or build destination batches.
Broad pathfinding, danger and unit-role timers remain in the normal performance
report. The analyzer can still read detailed CSVs in historical recordings.

Python event handlers and RFC turn-system entry points (including stability,
implosion, spawns, barbarians, religion, resources, unique powers, AI wars,
plague, victory and communications) use the Windows Python 2.4 `time.clock`
high-resolution wall timer. Timings are aggregated and written once per
EndGameTurn into the usual `turns.jsonl`, compressed on exit. These records
contain timing statistics rather than city/unit state.

The launcher automatically writes `performance-report.md` and
`performance-summary.json` in each game folder, under
`testing/runs/performance-600ad-150turns/`. To regenerate them manually:

```powershell
python testing/analyze_performance.py <run-or-batch-folder>
```

Inclusive times overlap nested measurements. Exclusive times subtract only
instrumented children in the same layer; DLL timings can include Python
callbacks, so do not add both layers together. Turn-boundary intervals include
UI/rendering waits as well as simulation. Instrumentation has overhead and
does not measure every function; compare matching builds/settings/seeds.

### Gameplay recordings

Both modes write `turns.jsonl`: metadata, an initial snapshot and state
snapshots at the configured interval (`--record-interval`, default 1).
The final state is always recorded, including when the limit is not a multiple
of the interval. The boundary is **after RFC end-turn implosion
processing and before the next turn's trade recalculation**, not an arbitrary
screen capture. Each record is appended and the file closed immediately,
keeping earlier lines readable if a later write is interrupted. Civ4's reduced
Python library has no `gzip` module, so the external Python 3 launcher compresses
the log to `turns.jsonl.gz` after its child game exits. If the launcher itself
is interrupted or compression fails, plain JSONL remains usable. The analyzer
accepts both formats and reports incomplete trailing records.

Events retain their actual game turn/year and are collected between snapshots.
Lightweight per-turn tracking preserves civic usage counts, first-establishment
dates and 0/10/25/50-turn establishment checkpoints even with sparse snapshots.
Records distinguish `elapsed_turns` from the engine's zero-based `turn` and
include `span_turns`; the analyzer does not count ten snapshots as ten simulated
turns. Population/army dominance peaks and diagnostic invariants are evaluated
only at snapshot boundaries, so sparse sampling can miss short-lived changes.

| Data | Balance | Diagnostics |
| --- | --- | --- |
| Seed, build fingerprint, speed, difficulty, game options and info ID dictionaries | Yes | Yes |
| Civilization population, cities, land, gold/rate, research/rate, era, tech count, power, army composition, civics, religion and stability | Yes | Yes |
| Basic city population, food, imports/exports, yields, happiness, health and slaves | Yes | Yes |
| War, city founding/conquest/razing, technologies, religion, victory and observed civic/alive/religion changes | Yes | Yes |
| Exact known-tech lists, unit positions/damage/XP/promotions | No | Yes |
| Buildings, specialists, production target/progress, occupation and city/tile culture | No | Yes |
| Routes with infrastructure efficiency, profit and net food; slave revolt chance | No | Yes |
| Initial terrain/features/resources/improvements/routes/owners and subsequent changes | No | Yes |
| Global food conservation and city export-cap checks | No | Yes |

Diagnostics are detailed observations, **not a replacement save format**:
they do not serialize every engine field, mission queue, plot culture or
private mechanic timer. Checkpoints preserve the full game state. Not every
custom event has a dedicated semantic label yet; many appear through city,
civic and alive-state changes. Balance-mode summaries do not claim to explain
the cause of a collapse or prove that a popular civic is overpowered.

Errors represent the implemented invariants or Python exceptions. A route
with zero efficiency at the recording boundary is marked **investigate**,
because connections may have changed before the next route recalculation.
The checks do not yet cover every civic, inheritance rule or slave transaction.

`started.json`, `heartbeat.json`, `complete.json` and `failed.json` communicate
progress with the launcher. Saves are written initially, periodically and at
completion when `--checkpoint-interval` is positive; use 0 to disable them.
Defaults are 100 turns for balance and 25 for diagnostics. Engine save/load
behavior still requires in-game validation. Observer logging failures disable
logging and are reported separately from gameplay exceptions.

## Analyze a run or batch

```powershell
python testing/analyze_observer.py testing/runs/<batch-directory>
python testing/analyze_observer.py testing/runs/<new-batch> --compare testing/runs/<baseline-batch>
```

This streams records into `report.md` and `summary.json`, including:

- Final survival/population (both all-game and survivor-only medians) and population
  shares at exact common 50-turn elapsed boundaries and the run end.
- Survival, population, technology count and power 0/10/25/50 turns after first
  establishment (first owned city, not necessarily the historical spawn turn).
- Labor civic starting spells, switch destinations and completed durations,
  separated from ongoing right-censored spells and deaths.
- Slave employment conditional on active Slavery, with assigned and free slaves
  separated. Snapshot counts are not extrapolated to city-turn exposure.
- Food by city size (1-3, 4-7, 8+): local production, imports, exports, consumption,
  surplus, storage fill, deficit samples and observed net population changes.
  Normal samples exclude disorder, anarchy, occupation and food-based production.
  Population losses alone do not establish famine.
- Semantic collapse events for barbarian losses, halved city count, lost homeland
  and stability civil war, distinguishing inheritance from full/partial fragmentation.
- Sparse labor evaluations copied from existing DLL calculations, including raw
  and current-civic-adjusted scores. These can originate in planning as well as
  revolution selection; they do not certify an actual switch. No civic scoring is
  re-run for reporting. Evaluations are sampled when current/best civic changes
  and at 25-turn boundaries when an evaluation occurs; sample frequency is biased
  towards changes and must not be interpreted as preference prevalence.
- A compact run-integrity table and grouped diagnostics with one traceback per
  error signature, affected seeds and first error turn.

Raw civic exposure, era dates and full findings remain in `summary.json`; the
main report omits raw civic-frequency lists, the fixed 40-percent dominance column
and repeated per-game tracebacks. Same-age 50-turn survival remains in an appendix;
all establishment checkpoints remain in the JSON.

With `--compare`, `comparison.md` pairs unique matching seeds with identical
settings, scenario, mode, recording interval and final turn. It reports paired
population/city/technology deltas at exact common boundaries, paired medians and
population-delta ranges. Each build pair remains separate. Missing/ambiguous
pairs and affected recordings are excluded, not converted to zero. In particular,
the previous 20-game batch has only nine games without recorded errors, so a
clean comparison cannot contain all twenty seeds. Error-free selection itself
may correlate with gameplay and is not a causal guarantee.

Only complete recordings without recording-integrity issues contribute to pooled
balance tables. Games with gameplay errors have their own explicitly qualified
tables and are excluded from matched comparisons. Duplicate seeds within a
cohort are excluded from pooled statistics. Different build
fingerprints, modes, AI-control settings, effective game settings and final
turns are separated into cohorts. Runs are not automatically independent:
avoid counting repeated seeds as additional independent evidence. Older recordings
remain readable; missing context, assigned/free slave splits and semantic collapse
events are reported as unavailable rather than inferred. Era-entry
dates include civilization spawns with advanced starting technologies.

Keep settings constant within an experiment and compare matching seeds across
builds. AI-only results measure the current AI; they do not establish human
multiplayer balance or synchronization. In-game startup, Python 2.4 execution,
AI control and multiplayer behavior have not been validated by this implementation.
